## Анализ разницы в задержках

Среднее время ответа во втором прогоне выше по нескольким причинам:

1. **Сценарий заказов теперь выполняется полностью**: создание заказа — это транзакционная операция с несколькими INSERT (orders, order_items, tickets), которая значительно тяжелее GET-запросов из первого прогона.
2. **Длительность теста**: 4 минуты вместо 1 минуты — база данных накапливает больше строк в таблице `orders` и `tickets`, что замедляет последующие запросы без кэша.
3. **Локальная среда**: оба прогона выполнялись на одной машине (`127.0.0.1`). 1000 VU k6-клиентов конкурируют с процессом backend за CPU и память.

## Вывод

Нефункциональное требование (время отклика ≤ 2 с при 1000 одновременных пользователях) **не выполнено**: среднее время 4 359 мс, p90 = 7 528 мс.

Ключевое достижение прогона: **все 44 053 запроса выполнены без единой ошибки**, в том числе сценарий создания заказов, который в предыдущем прогоне не работал из-за некорректных URL эндпоинтов и закрытого окна продаж.

Для выполнения нормативного требования необходимы:
- кэширование GET-запросов к каталогу (`/api/events`) на уровне Spring Cache / Redis;
- оптимизация пула соединений PostgreSQL (увеличение `spring.datasource.hikari.maximum-pool-size`);
- перенос нагрузочного тестирования на выделенный сервер (Railway / VPS), чтобы исключить конкуренцию k6 с backend за ресурсы.
